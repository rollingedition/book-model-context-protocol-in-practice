# Build a host that works through tickets

By the end of this chapter you can connect a host to several Model Context Protocol servers, give their tools names that can't collide, run a short loop in which a model calls tools and reads their results, answer a server's input requests on the user's behalf, put resources into the model's context, and work a queue of tickets through all of it. What this chapter says about a host holds for revision {{out:connect-two-servers:shop protocol revision}} of the specification and for the Python SDK, `mcp` {{version:mcp}}.

Every ticket is a customer's question to [the shop](#the-shop), a small online retailer of kitchen and garden goods, and the support team works each through a host. The shop's data holds {{out:work-the-ticket-queue:tickets worked}} such tickets, each tagged with the tool a correct agent calls first, and written the way customers write: typos, bare order numbers, wrong IDs, and six with instructions aimed at an agent. Each earlier chapter built one part the host needs. Chapter 1's host loop, `lib.host`, showed a model one ticket and the tools of one server, and read one choice ([Let a model choose the tool](#let-a-model-choose)). Chapter 9 added the host's own checks: pinned tool definitions and consent before side effects ([Ask for consent before side effects](#consent-before-side-effects)).

The Model Context Protocol (MCP) gives the host most of the work. According to the specification's architecture page, the host creates and manages the clients, enforces consent, handles the user's authorization decisions and aggregates context across clients, while each server sees only its own part of the conversation ([architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)). A support host that takes tickets one at a time from a queue has to do all of that for {{out:work-the-ticket-queue:tickets worked}} tickets in a row, against two servers: the shop's, and the partner's, a parcel-tracking server from the shop's delivery partner that [Draw the trust boundaries](#trust-boundaries) introduced.

The support host lives in a new module, `lib.ticket_host`. It holds one client per server and a few turns of model calls per ticket, and nothing more. Planning, memory and longer agent loops belong to building agents, which is outside this book, so this chapter stays on what MCP asks of a host. `lib.support_shop` is the shop's server as the support host meets it, gathering chapter 3's tools, chapter 5's confirmation for refunds above the policy limit, and chapter 4's policies as resources. `recordings/ticket_runs.py` records the book's model working through the queue, as the recording **`ticket-runs`**, which two of this chapter's examples replay and [Test a server and watch it run](#test-and-observe) reuses.

## Connect one client per server {#one-client-per-server}

A host that uses several servers holds several clients, and the specification is exact about the shape: "each client is created by the host and communicates with exactly one server" ([architecture](https://modelcontextprotocol.io/specification/2026-07-28/architecture/index.md)). At the pinned revision there is no `initialize` handshake to share, because every request carries its own protocol version and the client's capabilities in `_meta` ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)). What a client still learns is its server's era, whether that server speaks the pinned revision or a 2025 one. The specification asks clients to cache that era for the lifetime of the server process (stdio) or origin (HTTP) ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)).

The Python SDK offers a class for several servers, `ClientSessionGroup`, and it looks like the natural choice. At `mcp` {{version:mcp}} it isn't one. Its `connect_to_server` always calls `session.initialize()`, the 2025 handshake, and never sends the `server/discover` probe that the pinned revision starts with (`mcp/client/session_group.py`; [session groups](https://py.sdk.modelcontextprotocol.io/v2/client/session-groups/index.md)). The SDK's own servers speak both eras, so a group still connects, but on the older revision, where a server pushes its input requests instead of returning them in a Multi Round-Trip Request. That would quietly undo chapter 5.

A group can also take a session you already hold, through `connect_with_session`. The SDK's page suggests a `Client`'s session for that, which would be on the pinned revision ([session groups](https://py.sdk.modelcontextprotocol.io/v2/client/session-groups/index.md)). The group then only merges the lists. Its `call_tool` raises an error on an input request unless you pass `allow_input_required=True` and drive the rounds yourself (`mcp/client/session_group.py`). It also still refuses two tools with one name unless it renames them all, as [Name tools across servers](#namespace-tools) shows.

The support host uses one `mcp.Client` per server instead. Each runs in its default auto mode, which probes `server/discover` and falls back to the handshake only for a server that doesn't answer it (`mcp/client/client.py`). The host keeps the clients in a map keyed by a prefix from its own configuration: `shop` for the shop's server, launched over stdio from `lib.support_shop`, and `partner` for the partner's server, `lib.partner`, connected in-process. The code connects both, gives the shop's server to a `ClientSessionGroup`, and reconnects to it with the era the first connection learned.

[One client per server](../examples/connect-two-servers.py)

Both of the support host's clients settled on {{out:connect-two-servers:shop protocol revision}}, each on its own. The group, given the same shop server, settled on {{out:connect-two-servers:ClientSessionGroup protocol revision}}, an older revision.

The reconnect passed the cached `DiscoverResult` as `prior_discover`, with the revision as `mode`, which `Client` adopts with no probe. It spoke {{out:connect-two-servers:reconnect protocol revision}}. It sent no `server/discover`, a fact the example asserts rather than prints, and its first request was `{{out:connect-two-servers:reconnect first request}}`.

The reconnect launched a new server process, which goes past what the specification asks, a cache for one process's lifetime, into what it allows: a client **MAY** persist the era "across restarts of the same server configuration, re-probing if the cached assumption later fails" ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md)). A host that restarts stdio servers or reconnects to an HTTP origin saves one round trip per connection that way.

The prefixes belong to the host, not the servers. Each server names itself, here `{{out:connect-two-servers:shop server}}` and `{{out:connect-two-servers:partner server}}`, but nothing makes those names unique or stable, and at the pinned revision a server may leave its name out altogether (`mcp/client/client.py`, `server_info`). [Name tools across servers](#namespace-tools) builds on the prefixes.

**Working rule:** Give each server its own `Client`, in auto mode, under a key from the host's configuration. Cache each server's era for as long as its process or origin lasts, reuse it across restarts of the same configuration if you like, and probe again when a request fails with a version error. Don't use `ClientSessionGroup` at `mcp` {{version:mcp}}: its `connect_to_server` speaks only the 2025 handshake, and given `Client` sessions it adds merged lists but not the retry rounds or the host's own names. Check again at each SDK release, because a group that probes would remove the need for your own map.

## Name tools across servers {#namespace-tools}

With [one client per server](#one-client-per-server), the support host holds two lists of tools, and the model needs one. Tool names are unique only within one server, so two servers can offer the same name, and the specification expects that. A host that aggregates servers **SHOULD** disambiguate, such as by prefixing tool names with a server identifier. The server's `name` from `serverInfo` is not guaranteed to be unique across servers, so it **SHOULD NOT** be relied on for that ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)). A prefix also has to keep the name valid, and tool names **SHOULD** use only letters, digits, `_`, `-` and `.`, up to 128 characters ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).

The shop's case makes the collision concrete. The scenario in the example supposes that the partner's next release adds a tool named `get_order_status`, for its own delivery orders, beside `track_parcel`, so both servers offer a tool with that name and different meanings. `ClientSessionGroup` offers a hook, `component_name_hook`, that renames tools as they arrive. It renames every name from every server, though, not only the ones that collide. The SDK's own docstring example builds the new name from `serverInfo.name`, the name the specification says not to rely on (`mcp/client/session_group.py`; [session groups](https://py.sdk.modelcontextprotocol.io/v2/client/session-groups/index.md)). Without the hook, the group refuses the second server.

The support host names every tool `{prefix}.{tool}`. It uses `.` as the separator because `.` is in the allowed set and reads like a path. `TicketHost.route` turns a name the model used back into the server's prefix and the tool's name on the wire, and returns nothing for a name the host doesn't know.

[Two servers, one tool name](../examples/tool-name-collision.py)

Where the group raised `{{out:tool-name-collision:ClientSessionGroup}}` and kept only the shop's server, the support host kept both, and the model sees {{out:tool-name-collision:tools the model sees}} tools.

`shop.get_order_status` routes to `{{out:tool-name-collision:shop.get_order_status routes to}}`, and `partner.get_order_status` to `{{out:tool-name-collision:partner.get_order_status routes to}}`. A bare `get_order_status` routes to `{{out:tool-name-collision:get_order_status routes to}}`. That is the host declining to guess which server the model meant, so it sends the model an error result naming the problem instead.

Prefixing every name, not only the colliding ones, costs a few tokens per tool and buys stability. A name the model learned stays the same when another server adds a tool, so a recorded prompt, a prompt cache and a log line keep meaning the same thing. The client best practices page asks hosts to keep the `tools` array stable for the same reason: adding or removing tools mid-conversation invalidates the model provider's prompt cache ([client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)).

Before you settle on a separator, check that your model writes it back. The book's model wrote every name with a prefix the host knew. In the [queue run](#work-the-queue), each of its {{out:work-the-ticket-queue:tool calls}} tool calls ended as a result or a tool error, and none as an unknown tool. That is one model on one prompt. Another model may drop or rewrite a prefix, and then the error result is what tells it.

**Working rule:** Prefix every tool name with a key from the host's configuration, joined by `.` or `_`, and route each call back through your own map, never by `serverInfo.name`. Prefix all names, not only the ones that collide, so names stay stable when a server changes. Send an unknown or unprefixed name back to the model as an error instead of guessing.

## Run the host loop {#run-the-host-loop}

With [tools named across servers](#namespace-tools), the support host can let the model work a ticket. The host sends the model a system prompt with the tools and the ticket as the user's message. If the reply holds a tool call, the host checks it, runs it, and sends the result back as the next message. If the reply is words, the ticket is done. Everything a model can't be trusted to do sits in the host, between the reply and the call: the name is routed through the host's own map, the call passes chapter 9's consent gate ([Ask for consent before side effects](#consent-before-side-effects)), and the call has a timeout.

The tools page puts several of those duties on the client. Clients **SHOULD** give tool execution errors, results with `isError: true`, back to the model "to enable self-correction". They **SHOULD** also confirm sensitive operations with the user, show tool inputs before calling, validate results before passing them on, set timeouts and log tool use ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).

The support host sends every outcome back in a `<tool_response>` block, named by tool and outcome. The outcomes are a result, a tool error, a call the user declined, a name it doesn't know, and a call that failed, either by timing out after {{out:work-one-ticket:timeout per request, seconds}} seconds on one request or by running past the client's cap on input-request rounds. It stops a ticket after {{out:work-one-ticket:model calls allowed per ticket}} model calls, so a model that keeps calling tools can't run up a bill on one ticket.

The host's prompt is chapter 1's, with one paragraph added. That paragraph says that tool names start with their server, that results come back in `<tool_response>` blocks, that the model replies to the customer once it has what the ticket needs, and that it uses only order IDs, amounts and `quote_id`s that the ticket or a tool gave it. The prompt and the parsing stay in the book's code, as [Let a model choose the tool](#let-a-model-choose) recommends.

The model's replies come from the recording `ticket-runs`, which `recordings/ticket_runs.py` made with the book's model, Qwen3-4B-Instruct-2507, quantized to 4 bits and run on the CPU. It sampled at temperature {{out:work-one-ticket:sampling temperature}} with one fixed seed, {{out:work-one-ticket:sampling seed}}, as chapter 1's recording did, so another seed could give different replies. A recording answers only the exact messages it saw, and from the second turn on those messages hold tool results, so a replay also fails if a tool's output changes.

That is why `lib.support_shop` derives each `quote_id` from a counter, hashed with the shop's seed, instead of at random. A random `quote_id` would change every run, and with it every later turn. The ID looks random, such as `{{out:host-answers-elicitation:O-1145 quote id}}`, but it repeats exactly on every run and after every restart, when the counter starts again, so the same IDs come back naming different quotes. A replay needs that, and a server you ship must never do it. It keeps its IDs random, so no one can work one out ([Shape tools around tasks, not endpoints](#tasks-not-endpoints)).

Ticket T-0009 shows the loop when the first guess is wrong. The customer asks what a refund would be on order "o7144". The order they mean is {{out:work-one-ticket:order the customer means}}, and O-7144 doesn't exist.

[The host works one ticket](../examples/work-one-ticket.py)

The model went straight to `quote_refund`, with the order ID it read and a SKU, `KG-1031`, that the ticket never gave. That SKU is the example in the shop's tool descriptions. The call came back as a {{out:work-one-ticket:turn 1 outcome}}: the server said there is no such order and that `find_orders` lists the customer's orders. On the second turn the model took that advice and called `{{out:work-one-ticket:turn 2 tool}}` for the ticket's customer. With the list in front of it, the model didn't pick O-1744 for the customer. It answered: "{{out:work-one-ticket:turn 3 reply}}" The ticket took {{out:work-one-ticket:model calls}} model calls.

The error result did the job it was meant for. A host that swallowed the failure would have left the model to guess. The invented SKU is the second lesson: a model copies example values from descriptions into its arguments, so a server should reject arguments that don't match the order. The shop's `quote_refund` does that in other tickets of the [queue run](#work-the-queue), answering that the order has no line for that SKU. Examples in descriptions should also be values that can't be mistaken for real ones.

**Working rule:** Keep the loop in the host, short and bounded: route each call through your own map, pass it through consent, give it a timeout, and send every outcome back to the model, errors included, in a format your own code writes. Cap the model calls per ticket. Anything longer than a few turns, such as planning across tickets or memory, belongs in an agent framework, not in the host's protocol code.

## Answer input requests for the user {#answer-input-requests}

Some tool calls in [the host loop](#run-the-host-loop) don't finish on the first request. At the pinned revision, a server that needs something from the user returns an `InputRequiredResult` with `inputRequests` instead of a result. The client then retries the same call with `inputResponses`, echoing the server's `requestState` unchanged and using a new JSON-RPC `id` ([Multi Round-Trip Requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr.md)). [Return an input request instead of a result](#return-an-input-request) built the server's side, and this section is the host's, where the specification adds duties of its own. For elicitation, clients **MUST** make clear which server is asking, offer clear decline and cancel options, and, in form mode, let the user review and change answers before they are sent ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation.md)).

The Python SDK splits the work. `Client.call_tool` runs the retry loop itself, up to `input_required_max_rounds` rounds, and hands each elicitation to the client's `elicitation_callback` (`mcp/client/client.py`, `mcp/client/_input_required.py`). The callback receives the request and the session it arrived on, but not the host's name for that server. So the support host gives each client its own callback, bound to that client's prefix. The callback passes the prefix and the request to the person who answers for the host, whom the code calls the lead, and records the request and the answer in `host.asked`.

The shop's API holds a refund above the refund policy's limit of €{{out:host-answers-elicitation:refund policy limit}} until a support lead releases it, and `issue_refund` asks for that release with a one-field form. Two such refunds run through the support host's own `call` method, the path a model's tool call takes, and a scripted lead accepts the first and declines the second.

[The host answers an input request](../examples/host-answers-elicitation.py)

Each time, the lead saw which server asked and its message. For the first refund, the server asked from `{{out:host-answers-elicitation:O-1145 asked by}}`, and its message read: {{out:host-answers-elicitation:O-1145 message}} The form had one field, `{{out:host-answers-elicitation:form fields}}`. The lead's {{out:host-answers-elicitation:O-1145 lead's answer}} released the refund, and the model would read the refund, with its ID and the status `requested`.

The second refund was declined. After the lead's {{out:host-answers-elicitation:O-2289 lead's answer}} for order O-2289, the server raised a tool error, and the model would read: {{out:host-answers-elicitation:O-2289 back to the model}} That error result is what lets the model tell the customer the truth: the refund is waiting for a person.

Both refunds also passed chapter 9's consent gate before either reached the server, and the host asked the user about `{{out:host-answers-elicitation:consent asked for}}`. Consent and the server's confirmation answer different questions. Consent asks whether a call should happen at all, for any server. The confirmation is the shop's server asking about one refund that its own policy holds, and only a server that chooses to ask will ask ([Ask for consent before side effects](#consent-before-side-effects)).

Each call here took one retry round, out of the {{out:host-answers-elicitation:retry rounds allowed per call}} that `Client` allows by default. A server that keeps asking past that cap makes `call_tool` raise `InputRequiredRoundsExceededError`, which the support host sends back to the model as a `failed` call, like any other failure. A host that expects longer exchanges raises the cap or drives the rounds itself with `client.session.call_tool(..., allow_input_required=True)`, as [Resume the call with the answer](#resume-with-the-answer) does.

In URL mode, an `accept` means only that the user agreed to the interaction, not that they finished it ([elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation.md)). So the host shows the full URL, asks before opening it, and never opens it on its own.

**Working rule:** Give each client its own elicitation callback that knows which server it belongs to, and show the user that server's name with its message, the fields and a way to decline. Return a decline to the model as the server's error, not as silence, so the model can say what happened. Keep consent in the host as well, because the server's question covers only what the server chooses to ask.

## Put resources in the model's context {#resources-in-context}

Resources bring documents into the model's context, and the host decides which. The specification calls resources **application-driven**: hosts decide how to use them, whether by letting the user pick, by their own heuristics, or by asking the model ([resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources.md)). Nothing arrives in a model's context because a server listed it. A server can help with annotations: `audience` says whether a resource is for the `user` or the `assistant`, and `priority`, from 0 to 1, says how much it matters. Clients can use both to filter and to choose what to include ([resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources.md)).

The shop's server lists its {{out:attach-a-policy-resource:policies listed}} policies as resources, with the annotations that [Expose the policies as resources](#policies-as-resources) gave them. All are for the assistant. The refund policy has priority {{out:attach-a-policy-resource:refund policy priority}}, and the others have {{out:attach-a-policy-resource:other policies' priority}}. The refund policy matters most to the model, because it says what may be refunded and that a refund above the limit waits for a lead. The support host's rule is its own: attach every resource the server marks for the assistant with a priority of at least {{out:attach-a-policy-resource:attach at priority at least}}, once, after the tools in the system prompt. The model never chooses, so a ticket's text can't pull a document into the context.

[The host attaches a policy](../examples/attach-a-policy-resource.py)

The host attached one policy out of the {{out:attach-a-policy-resource:policies listed}} listed, and that is `{{out:attach-a-policy-resource:attached}}`, the one at priority {{out:attach-a-policy-resource:refund policy priority}}.

Its text took {{out:attach-a-policy-resource:of which the policy}} of the system prompt's {{out:attach-a-policy-resource:system prompt, characters}} characters, a cost paid on every model call for every ticket. The server marked the read cacheable for {{out:attach-a-policy-resource:ttl ms}} milliseconds, and the SDK's `Client` honours that hint by default (`mcp/client/client.py`, `cache`). So the host read the policy twice, and the wire shows {{out:attach-a-policy-resource:resources/read sent to the server}} `resources/read` request.

Annotations are the server's opinion, and the shop's server is the shop's own, so its priorities are worth following. A server you don't run could mark a long document at priority 1.0 to fill the model's context, or dress an instruction up as a policy. The specification treats a server's tool annotations as untrusted unless the server is trusted ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)), and the same caution fits resource annotations. Attaching per kind of ticket, such as the refund policy only for refund tickets, saves tokens but needs the host to classify tickets before the model reads them. We recommend the fixed rule until the context's cost says otherwise.

**Working rule:** Decide in the host which resources reach the model, by rules you can state: a fixed list, or annotations from servers you trust, with a cap on their size. Read them through the client's cache. Let the user add a resource for one ticket when the rule misses it, and never let the model or a ticket's text choose on its own.

## Work through the ticket queue {#work-the-queue}

The pieces so far work one call or one ticket. A support queue runs them for every ticket in turn, through one host and one connection per server, and that is where a host learns what its model does over many tickets rather than one. This run takes all of the shop's tickets, in order, through both servers with the refund policy attached. The people are the scripted ones from [Answer input requests for the user](#answer-input-requests): a user who approves every consent question, and a lead who declines every input request.

A run is scored by comparing the first tool the model called with the tag each ticket carries in the shop's data, under one rule. `lib.shop_data` tags a refund request with `issue_refund`, the tool that makes the refund, but `issue_refund` takes a `quote_id`, so a correct run starts with `quote_refund`. `ticket_host.expected_first_tool` applies that rule, and [Measure how often the right tool is chosen](#tool-selection-accuracy) scores the same way. The counts also cover what matters more than the first tool: whether refund tickets ever reached `issue_refund`, and what the host asked the user.

The recording `ticket-runs` holds the model's replies for this run's {{out:work-the-ticket-queue:model calls}} model calls, and it was made in {{out:work-one-ticket:recording batches}} batches, one command each. Each command replayed the replies already recorded before calling the model, so the shop's state was the same in every batch.

Of those batches, {{out:work-one-ticket:single-ticket batches}} worked a single ticket, T-0007, and the rest worked the queue. The queue's replay uses the single-ticket batch's replies for T-0007, because its messages match. By the manifest's timings, a call took {{out:work-one-ticket:seconds per model call, mean}} seconds on average on the CPU, and the longest batch took {{out:work-one-ticket:longest batch, minutes}} minutes. The manifest, in `examples/data/recorded/ticket-runs/`, lists the batches, the model file by revision and hash, the sampling, the prompt's hash and the host's settings.

[The host works the queue](../examples/work-the-ticket-queue.py)

Most runs began with the right call: the first tool matched the ticket's tag, under the refund rule, for {{out:work-the-ticket-queue:first tool as tagged}} tickets. The host worked {{out:work-the-ticket-queue:tickets worked}} tickets with {{out:work-the-ticket-queue:tool calls}} tool calls, and {{out:work-the-ticket-queue:outcome tool error}} of those were tool errors that went back to the model.

Nothing ran out of turns: {{out:work-the-ticket-queue:stopped at the turn limit}} tickets stopped at the limit of {{out:work-one-ticket:model calls allowed per ticket}} model calls.

The refund tickets tell a different story. Of the tickets that asked for a refund, {{out:work-the-ticket-queue:issue_refund tickets that called issue_refund}} reached `issue_refund`, and the host issued {{out:work-the-ticket-queue:refunds issued}} refunds.

Yet the replies to {{out:work-the-ticket-queue:issue_refund tickets promising a refund that never ran}} told the customer a refund would be made, by the phrases `ticket_host.promises_refund` looks for. Ticket T-0048's reply reads: "{{out:work-the-ticket-queue:T-0048 reply}}" The dollar sign is the model's, because the API's amounts carry no currency and the shop's are in euros. No refund was made, and the amount it promises is above the €{{out:host-answers-elicitation:refund policy limit}} limit that the attached policy states.

The tickets tagged `quote_refund`, which ask what a refund would be, are the clearer case of a reply as the model's claim. The replies to {{out:work-the-ticket-queue:quote_refund tickets promising a refund that never ran}} promised one anyway, and none called `issue_refund`.

Of the tickets with instructions aimed at an agent, {{out:work-the-ticket-queue:injected tickets that called issue_refund}} called `issue_refund`. Since no ticket refunded anything, that says little about injection. [Treat ticket text as untrusted data](#untrusted-tool-output) is where to look.

The host asked the user {{out:work-the-ticket-queue:consent questions}} consent questions, for `{{out:work-the-ticket-queue:consent asked for}}`. The partner's `track_parcel` was the only tool the model called that is outside the host's list of calls it allows without asking (`host_guard.NO_SIDE_EFFECTS`, [Ask for consent before side effects](#consent-before-side-effects)). `issue_refund` is outside that list too, but the model never called it.

For ticket T-0003 the model called `{{out:work-the-ticket-queue:T-0003 tool}}` with the tracking number `{{out:work-the-ticket-queue:T-0003 tracking number}}`. In the recording that [Catch poisoned tool descriptions](#tool-poisoning) uses, which has unprefixed names and no policy attached, the same ticket went to `get_order_status`: another prompt, another choice. That tracking number is the example in the tool's own description, not anything the customer wrote, and the partner's example server answers any well-formed number, so the customer was told where a parcel was. The scripted user approved, and a person reading the question would have seen a number the ticket didn't contain.

This is one run of one model, on one prompt, with one seed, sampled at temperature {{out:work-one-ticket:sampling temperature}}. Another seed could give different replies and different counts, so the run measures that setup, not models in general. It shows what the host has to catch, not how often this model gets refunds wrong; [Measure how often the right tool is chosen](#tool-selection-accuracy) measures over the same recording. A better prompt or a stronger model may close the refund gap, and the host still has to check, because the reply is the model's claim and the call log is the record.

**Working rule:** Treat the model's last reply as a draft and the host's call log as what happened. Before a reply reaches a customer, compare its promises with the calls that ran, and send a ticket to a person when they differ, such as a refund ticket with no refund made. Strip any handle, such as a `quote_id`, from a reply before it goes out. Score a run on outcomes, not only on the first tool, and record a run of the whole queue each time you change the prompt, a description or the model.

## What goes wrong in production {#build-a-host-in-production}

In production the same parts fail in ways a replayed run never shows, each with a sign to watch for.

**The tool list outgrows the context.** Every tool's definition goes into every model call. The support host's {{out:attach-a-policy-resource:tools the model sees}} tools and one policy already make a system prompt of {{out:attach-a-policy-resource:system prompt, characters}} characters, as [Put resources in the model's context](#resources-in-context) measured. Each server you add pays that again on every turn of every ticket. The client best practices page suggests switching to progressive discovery, a small search tool that returns definitions on demand, once definitions take more than a threshold share of the context window, "for example, 1%-5%" ([client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)). That threshold is a rule of thumb, not a measurement. The sign is time to first token rising with each server, and tool choices getting worse as the list grows.

**A changing tool list breaks the prompt cache.** A server that adds or removes a tool mid-conversation changes the `tools` array, and the provider's prompt cache with it ([client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices.md)). The support host lists tools once per connection and prefixes every name, so a new tool on one server doesn't rename the others. When a `list_changed` notification arrives, apply the new list between tickets, not inside one, and run it past chapter 9's pins first ([Pin tool definitions and flag changes](#pin-tool-definitions)).

**A server dies or a stream breaks mid-call.** The specification asks a client to restart a stdio server that exits, and in-flight requests "are simply lost" ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md)). Over Streamable HTTP, a broken response stream also loses its request, because the pinned revision removed resumable streams. The client **MUST** then send the request again as a new request with a new ID ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)).

The support host reports a failed call to the model as `failed` and moves on. A host you ship reconnects and retries reads. It retries a refund only where the server's once-only record and its quotes outlive the server's process, as chapter 6's shared store does ([Run replicas without sticky sessions](#scale-without-sessions)). `lib.support_shop` keeps both in its process, and its quote IDs repeat after a restart, so a retried `quote_id` could name a new quote for another order. With a server like that, the host asks a person instead of retrying a refund.

**A tool goes missing over HTTP.** At the pinned revision a tool can mark arguments with `x-mcp-header`, which the client copies into `Mcp-Param-*` headers, and a client **MUST** drop from `tools/list` any tool whose `x-mcp-header` is invalid ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)). The SDK does this for you, so the sign is a tool the server's own listing has and the model never sees. Log the count of tools per server at each connection.

**A server's claims reach the model unchecked.** Tool annotations from a server you don't trust are claims, not facts ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)), and so is a tool's output. In the [queue run](#work-the-queue), the partner's example server answered a tracking number the model copied from the tool's description, and the customer was told where a parcel was. Treat what a server returns as data about that server's answer, not as the truth about the order, and check it against the system of record before it reaches a customer.

**The host's own trust is still too wide.** The support host runs the shop's server over stdio, without OAuth, with chapter 3's tools, which trust the `customer_id` the caller sends. In production the host reaches the shop's server over Streamable HTTP, with a token per member of the support staff ([Authorize clients with OAuth](#authorization)). That token's subject is the staff member, a staff ID such as `{{out:token-with-pkce:token sub}}`. The server never takes the acting user from a tool argument. It takes the customer from the ticket record it looks up, and checks it against what that member of staff may handle. Only where customers sign in themselves is the subject the customer ([Keep the server from acting as a confused deputy](#confused-deputy)). The support host's scripted user approves every call. A real one reads each question.

**Working rule:** Before the host goes to production, log per ticket the tools offered, every call with its outcome, every consent question and input request, and the model's last reply, so a bad answer can be traced to the turn that caused it. Watch the size of the tool list per model call, reconnect and retry on a lost call, and keep every server's tool list and pins under the host's control.

## Decisions this chapter made {#build-a-host-decisions}

- **One `mcp.Client` per server, in auto mode,** under a prefix from the host's configuration. No `ClientSessionGroup`: at `mcp` {{version:mcp}} its `connect_to_server` speaks only the 2025 handshake, and with `Client` sessions it adds neither the retry rounds nor the host's names.
- **Each server's era is cached** as its `DiscoverResult` and reused on a reconnect, even of a restarted server, as the specification allows, so a reconnect sends no probe. A version error means probing again.
- **Every tool is named `{prefix}.{tool}`,** for every server, not only on collision, and never from `serverInfo.name`. An unknown name goes back to the model as an error.
- **Chapter 9's pins and consent gate sit in front of every call.** The host pins each server's definitions at its first connection, standing in for the user's approval.
- **Each client has its own elicitation callback,** bound to its server's prefix, so the person answering always sees which server asks.
- **The host, not the model, attaches resources:** those the shop's server marks for the assistant at priority {{out:attach-a-policy-resource:attach at priority at least}} or more, which is the refund policy alone.
- **The loop is thin:** at most {{out:work-one-ticket:model calls allowed per ticket}} model calls per ticket, a timeout of {{out:work-one-ticket:timeout per request, seconds}} seconds per request, every result and error back to the model in a `<tool_response>` block. Planning and memory belong to an agent framework.
- **The shop's server for the host gathers chapters 3 to 5** in `lib.support_shop`, with quote IDs hashed from a counter so a recorded run replays. They repeat after every restart, which a server you ship must never do.
- **A refund ticket counts as right when it starts with `quote_refund`,** because `issue_refund` needs a quote. Chapter 11 scores the same way.
- **The recording `ticket-runs` is one model's behaviour on one prompt,** recorded in batches that each replay what came before, so the shop's state is the same in every batch.
