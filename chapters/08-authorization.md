# Authorize clients with OAuth

By the end of this chapter you can protect the shop's Model Context Protocol server with OAuth. You publish the metadata that leads a client to the authorization server, identify the support team's host with a Client ID Metadata Document, get tokens with PKCE, accept only tokens issued for the shop's server, catch a mix-up attack through the issuer of each response, and require a scope per tool, with step-up when a refund needs more. Where this chapter describes the specification it means revision {{out:serve-on-loopback:protocol revision}}, and where it describes the Python SDK it means `mcp` {{version:mcp}}.

The support team at [the shop](#the-shop), a small online store for kitchen and garden goods, answers customer tickets through a host. [Serve over Streamable HTTP](#streamable-http) moved the shop's server, `shop-support`, onto an HTTP address so that those hosts could share it. Its Origin check keeps out web pages and nothing else: any program that reaches the port can read orders and issue refunds ([Reject requests from other origins](#validate-origin)). The shop therefore needs to know which host is calling, for which person, and what that person may do. Support staff may read orders and stock; only a support lead may refund.

The Model Context Protocol (MCP) answers with OAuth 2.1, and authorization is optional in MCP. It belongs to HTTP transports: a stdio server takes its credentials from the environment instead ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). A protected MCP server is an OAuth resource server, the host's client for it is an OAuth client, and an authorization server issues the tokens, either beside the MCP server or apart from it. You know this flow from the client side of other APIs. What MCP changes is that a client knows nothing about a server in advance. It starts from a URL, so discovery, the client's identity and the token's audience all have to work with no setup between the two.

Four shared modules in `examples/lib/` carry this chapter's setup, so each example shows only its idea:

- `lib.auth_server` is the shop's authorization server, on loopback: metadata, the authorization code grant with PKCE, `iss` on every answer, and JWT access tokens bound to one server. Consent is scripted, standing in for the person at the browser. It is a teaching server for these loopback examples, and you must never deploy it. It signs no one in, and its signing key derives from the book's public seed, so anyone with the book can mint tokens it accepts. A deployment uses an established authorization server that meets this chapter's checks. The Python SDK has an authorization server of its own, but its documentation discourages it for new servers, and its metadata advertises neither `iss` nor Client ID Metadata Documents ([SDK authorization docs](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.3.0/docs/run/authorization.md)).
- `lib.oauth_client` is the host's side: the SDK's `OAuthClientProvider` with in-memory token storage, and a scripted browser that follows the authorization server's redirects and hands the answer back to the SDK.
- `lib.tool_scopes` adds the per-tool scope check that the SDK doesn't have.
- `lib.protected_shop` puts them together: chapter 3's five tools behind OAuth, as this chapter leaves them.

Everything runs on 127.0.0.1 over plain HTTP. That is acceptable for local development only. In production, every authorization server endpoint MUST be served over HTTPS ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)).

## Find the authorization server from the resource {#protected-resource-metadata}

A client that has only a server's URL must learn from the server where to get a token, and the pinned revision does this in two steps. First, MCP servers MUST publish Protected Resource Metadata (RFC 9728), a JSON document that names the resource and lists at least one authorization server ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). A request without a token gets 401, and its `WWW-Authenticate` header points to that document in a `resource_metadata` parameter. A client that finds no such parameter tries the well-known URI, `/.well-known/oauth-protected-resource` with the server's path inserted, and then without the path ([authorization server discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)). Second, the client fetches the authorization server's own metadata (RFC 8414), which lists its endpoints and what it supports.

Two values must match along the way. The `resource` in the server's metadata must be identical to the URL the client used, or the client must not use the metadata ([RFC 9728, section 3.3](https://www.rfc-editor.org/rfc/rfc9728.txt)). And the `issuer` in the authorization server's metadata must be identical to the issuer the client built the well-known URL from ([RFC 8414, section 3.3](https://www.rfc-editor.org/rfc/rfc8414.txt)). Both checks stop a client from trusting a document that describes some other server.

This server states its own URL, and the authorization server states its issuer. The SDK does the server's half when you give `MCPServer` an `AuthSettings` and a token verifier: `issuer_url` names the authorization server, `resource_server_url` is the server's own endpoint URL, and `required_scopes` lists the scopes every request needs. The shop's server requires `orders:read` and `stock:read`, because every ticket needs one or both. `refunds:write` comes later, and only when a refund needs it. The token verifier is `lib.auth_server.JwtVerifier`, which checks a token's signature, issuer and expiry. On loopback the port, and so the resource URL, is known only once the socket is open. So the server is built in a function of its base URL, and `serve_built` from `lib.auth_server` opens the socket first. Then the example plays a client: it sends `tools/list` with no token and follows the answer.

[Follow the 401 to the authorization server](../examples/discover-the-authorization-server.py)

The chain holds at each step, and the output beside the example shows the values. The first request got {{out:discover-the-authorization-server:status}}, and its challenge names `{{out:discover-the-authorization-server:challenge error}}` as the error. That error is the SDK's choice, and a departure from RFC 6750, which says a server SHOULD NOT include an error code when a request carries no credentials at all ([RFC 6750, section 3.1](https://www.rfc-editor.org/rfc/rfc6750.txt)). The metadata URL's path is `{{out:discover-the-authorization-server:resource metadata path}}`, the well-known prefix with the server's path inserted, as RFC 9728 asks. The metadata names the endpoint's own URL as its resource, lists {{out:discover-the-authorization-server:authorization servers}} authorization server, and gives `scopes_supported` as `orders:read stock:read`, which the SDK fills from `required_scopes`.

The challenge has no `scope` parameter, because the SDK's 401 never sends one (`mcp/server/auth/middleware/bearer_auth.py`). So a client falls back to `scopes_supported`. The specification's order is the challenge's `scope` first, then every scope in `scopes_supported`, then no `scope` at all ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). That is why `scopes_supported` should be the smallest set that works, not every scope the server knows: whatever it lists, every host asks every user for.

The authorization server's metadata has the issuer the client fetched it by, and the server advertises Client ID Metadata Documents and `iss` on authorization responses. Each of the three is an assert, so a server that stopped advertising one would fail its run. The server's PKCE methods are `{{out:discover-the-authorization-server:code_challenge_methods_supported}}`, which the next sections rely on. The SDK's client makes the issuer check for you. It raises `OAuthFlowError` when the metadata's `issuer` differs from the expected one, compared as plain strings ([SDK migration guide](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.3.0/docs/migration.md)). Its resource check is laxer than RFC 9728: it accepts metadata whose `resource` is a same-origin path prefix of the server's URL (`mcp/shared/auth_utils.py`). A `validate_resource_url` callback on `OAuthClientProvider` replaces that check with your own.

**Working rule:** Give every protected server an `AuthSettings` with its endpoint's URL as `resource_server_url`, exactly as clients will type it, and the smallest `required_scopes` that every request needs. Check the chain with one request that carries no token: a 401, a `resource_metadata` URL, metadata whose `resource` is the endpoint, and authorization server metadata whose `issuer` is the URL you fetched it from. When a value differs by a trailing slash or a port, fix the configuration rather than relaxing the client.

## Identify the client with a metadata document {#client-id-metadata-documents}

[Find the authorization server from the resource](#protected-resource-metadata) tells the host where to get a token. The authorization server still has to know which client is asking, and a host meets MCP servers it has never seen, so it can't have registered with each one's authorization server in advance. The pinned revision ranks the ways to get a client ID. It uses pre-registered client information if there is any. Otherwise it uses a Client ID Metadata Document, if the authorization server advertises `client_id_metadata_document_supported`. Otherwise it uses Dynamic Client Registration, and otherwise it asks the user ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).

A Client ID Metadata Document makes the client ID a URL. The client publishes a JSON document at an `https://` URL with a path, and that URL is its `client_id`. The document must contain at least `client_id`, equal to the URL exactly, `client_name` and `redirect_uris` ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). The authorization server fetches the document when the client first appears, checks the ID and the redirect URI against it, and may cache it by its HTTP headers. It must not follow redirects while fetching, and it must not cache an error ([metadata document draft -02](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.txt)).

A document can't carry a shared secret, because `client_secret` is forbidden. A client identified this way is therefore public, and it relies on PKCE, or proves itself with a key pair through `private_key_jwt` ([draft -02, section 4.1](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.txt)). The MCP specification links draft -00 of that document, and we cite draft -02, the later text. A client ID from a document works with any authorization server. A pre-registered or registered client ID, by contrast, is bound to the server that issued it, and the pinned revision forbids reusing it with another ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).

Dynamic Client Registration is deprecated at the pinned revision. It stays as a fallback for authorization servers without metadata document support, and its earliest removal is the first revision released on or after 2027-07-28 ([deprecated features](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)). [Replace dynamic client registration](#replace-dynamic-registration) moves a client off it.

The support team's host publishes its document at `https://support.fernhill.example/oauth/client.json`. Nothing here reaches a network, and `fernhill.example` never resolves, so the shop's authorization server can't fetch it. Rather than give the host an `http://` client ID that a loopback server could fetch, `lib.auth_server` keeps the document in a mapping from client ID URL to document. That mapping stands in for the fetch, and the server applies to it the checks it would apply to a fetched copy. This is pre-registration of the URL, which the draft allows as associating a client ID URL with its metadata "through other means" ([draft -02, section 5](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.txt)). It is a test-only stand-in, and a deployed authorization server fetches the document over HTTPS.

Running the server's checks on the document and on three broken copies, handing the SDK an `http://` client ID, and connecting twice, once to a server that supports metadata documents and once to one that doesn't, shows what each side does with a client ID it can't fetch.

[Publish the host's metadata document and use it](../examples/publish-client-metadata.py)

The document names `{{out:publish-client-metadata:client_id}}` as its own ID, and its redirect URI is `{{out:publish-client-metadata:redirect_uris}}`. Its token endpoint authentication method is `{{out:publish-client-metadata:token_endpoint_auth_method}}`, so the host holds no secret. The authorization server accepts the document as published. A copy with a secret fails with "{{out:publish-client-metadata:document with a secret}}", and the output beside the example gives the reason for the other two broken copies: one whose `client_id` names another site, and one whose client ID is on `http`. The SDK makes the same `https` check on its side. Given an `http://` client ID, `OAuthClientProvider` raises a `ValueError` as soon as it is built (`mcp/client/auth/utils.py`).

The SDK's client uses the document's URL as its client ID, and it falls back quietly when the server doesn't support that. Against the shop's authorization server it sent `{{out:publish-client-metadata:client_id sent}}` as the client ID, and made no registration request. Against a server that doesn't advertise support, it fell back to Dynamic Client Registration without a word, and the flow ended with "{{out:publish-client-metadata:without metadata document support}}", because the shop's authorization server has no registration endpoint. The SDK's documentation calls this fallback silent ([OAuth clients](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.3.0/docs/client/oauth-clients.md)). For the host, an authorization server without metadata document support shows up as a registration error, not as a missing feature.

**Working rule:** Give every host one Client ID Metadata Document at a stable `https://` URL, with only the redirect URIs it uses and no secret, and pass that URL to the SDK as `client_metadata_url`. Use pre-registered credentials where an authorization server has issued them, since they rank first, and keep Dynamic Client Registration only for authorization servers that support nothing else. In tests on loopback, keep the client ID an `https://` URL and associate it with a local copy of the document in the test authorization server, rather than giving the client an `http://` ID that no production server accepts.

## Get a token with PKCE {#authorization-code-with-pkce}

With its client ID from [Identify the client with a metadata document](#client-id-metadata-documents), the host can ask for a token. MCP uses the authorization code grant. The host sends the user's browser to the authorization server's authorization endpoint, the user signs in and consents, and the browser returns to the host's redirect URI with a code. The host then exchanges that code for a token at the token endpoint. Three parameters of that exchange carry most of its security.

PKCE binds the code to the client that asked for it. The client makes a random `code_verifier`, sends its SHA-256 hash as `code_challenge` with `code_challenge_method=S256`, and reveals the verifier only in the token request, so someone who intercepts the code doesn't have it. MCP clients MUST use PKCE with `S256`, and MUST refuse to go on if the authorization server's metadata has no `code_challenge_methods_supported` ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). The `plain` method, where the challenge is the verifier itself, is one OAuth 2.1 forbids explicitly from draft-16 on ([OAuth 2.1 draft-16, section 7.5.2](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-16.txt)). The MCP specification cites draft-13, which still allowed it ([OAuth 2.1 draft-13](https://www.ietf.org/archive/id/draft-ietf-oauth-v2-1-13.txt)).

The `resource` parameter (RFC 8707) names the server the token is for, by the server's canonical URI. MCP clients MUST send it in both the authorization request and the token request, whether or not the authorization server supports it ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). And `state`, which the client checks when the browser returns, ties the answer to the request.

The SDK's client runs that whole flow for the host, which lets the example watch it from the authorization server's side. `lib.oauth_client.connect` gives the client an `OAuthClientProvider` with the host's metadata document URL and a scripted browser in place of a person. The browser opens the authorization URL, follows the redirects, and stops at the first one addressed to the redirect URI. The authorization server's consent is scripted too: the signed-in user grants every requested scope that their role allows. A call to `get_order_status` runs the flow, the example reads what the server logged, and three requests the SDK never sends test what it refuses.

[Get a token with PKCE and use it](../examples/token-with-pkce.py)

The call worked, and order O-1873 is {{out:token-with-pkce:O-1873 status}}. The authorization request used the `{{out:token-with-pkce:code_challenge_method}}` method, and its challenge is the hash of the verifier that the token request revealed. Both requests named the same resource, the endpoint's URL. Each of these checks is an assert, so a change that breaks one fails the run. The access token is a JWT whose `aud` is the server's URL and whose `iss` is the authorization server. Its scope is `{{out:token-with-pkce:token scope}}`, the server's `scopes_supported`, because the 401 named no scope.

The token's `sub`, `{{out:token-with-pkce:token sub}}`, names the member of the support staff the host acts for, not a customer, and a server reads it from the SDK's `get_access_token().subject`. So a staff token can't by itself replace `SHOP_CUSTOMER_ID`, which the order completion in [Complete arguments for the user](#argument-completion) read from its environment over stdio. For a support host, the customer comes from the ticket record, which the server looks up and checks, never from a tool argument. Only where customers sign in to a host themselves is `sub` the customer, the case [Keep the server from acting as a confused deputy](#confused-deputy) takes up. There is no refresh token ({{out:token-with-pkce:refresh token}}): the shop's authorization server issues none, and the specification tells clients not to assume one ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).

The three requests the SDK never sends show what PKCE and single-use codes stop. The same code sent a second time got {{out:token-with-pkce:code sent twice}}, because a code works once. A fresh code sent with a guessed verifier got {{out:token-with-pkce:wrong verifier}}, so a stolen code alone is worth nothing. A request with `plain` got "{{out:token-with-pkce:plain method}}", because the shop's authorization server accepts only `S256`.

One check falls to the host. The SDK's client always sends `S256`, but it never reads `code_challenge_methods_supported`, so it goes ahead with an authorization server whose metadata leaves the field out (`mcp/client/auth/oauth2.py`). A host that must meet the specification fetches each authorization server's metadata itself before it connects, and it refuses any server that doesn't list `S256`.

**Working rule:** Let the SDK's `OAuthClientProvider` run the authorization code flow, and check once, from the authorization server's side, what it sends: `S256`, `state`, and a `resource` equal to the server's URL in both requests. Add the check the SDK skips, and refuse an authorization server whose metadata doesn't list `S256`. On an authorization server you run, accept only `S256`, make codes single-use and short-lived, and bind each code to its client, its redirect URI and its resource.

## Bind each token to one server {#token-audience}

The token from [Get a token with PKCE](#authorization-code-with-pkce) names the shop's server in `aud`, because the host sent `resource`. That protects no one unless the server checks it. An access token is a bearer credential, so whoever holds it can present it. Suppose the support host also connects to a partner's MCP server that trusts the same authorization server. The partner's server receives the tokens the host gets for it. If the shop's server accepted them, the partner's operator could replay them at the shop. RFC 8707 says the authorization server SHOULD restrict each token's audience to the requested resource, so that a token "legitimately presented to a resource cannot then be taken by that resource and presented elsewhere" ([RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.txt)). The other half belongs to the server: MCP servers MUST validate that a token was issued for them as its audience, and MUST NOT accept or pass on any other token ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).

In the Python SDK at `mcp` {{version:mcp}}, the server's half is off by default. `AuthSettings.validate_token_resource` decides whether the server refuses a token whose `AccessToken.resource` isn't `resource_server_url`. Left unset, it warns with `MCPDeprecationWarning` and behaves as `False`, and version 3.0 makes `True` the default (`mcp/server/auth/settings.py`). The SDK compares the two as URLs. The case of the scheme and host, a default port or a trailing slash makes no difference (`mcp/server/auth/middleware/bearer_auth.py`), and the comparison uses whatever your token verifier puts in `AccessToken.resource`. The other way is a verifier that checks `aud` itself.

Presenting one token to the shop's server several ways shows which check does the work. Two tokens are signed with the key of the shop's authorization server, one for the shop's server and one for the partner's, `https://partner.example/mcp`. Each is presented to the shop's server in three configurations: the SDK's default, `validate_token_resource=True`, and a verifier that passes the shop's URL to the JWT library as the expected audience.

[Present a token for another server](../examples/wrong-audience-rejected.py)

With the SDK's default, the partner's token got {{out:wrong-audience-rejected:SDK default, partner's token}}, and the server listed its tools for a token issued to someone else. The only sign was a warning at startup, {{out:wrong-audience-rejected:SDK default, warnings}}. Either check refuses the partner's token. With `validate_token_resource=True` it got {{out:wrong-audience-rejected:validate_token_resource=True, partner's token}}, and with the audience check in the verifier it got {{out:wrong-audience-rejected:verifier checks aud, partner's token}}. Both refusals are 401 with `invalid_token`, the answer the specification gives for a token that isn't valid for the server. The shop's own token was accepted in all three configurations, and neither fix warned.

We recommend `validate_token_resource=True`, which `lib.protected_shop` sets. It states the decision beside the server's other authorization settings, and it survives a change of token verifier. Check `aud` in the verifier as well when the verifier decodes the token anyway, since the second check costs nothing.

**Working rule:** Set `validate_token_resource=True` on every protected server, and make the token verifier fill `AccessToken.resource` from the token's `aud`. Treat an `MCPDeprecationWarning` from `AuthSettings` as a failed deployment, not as noise. Test the check with a token for another resource from the same authorization server, which must get 401. A server that calls another service on a client's behalf gets its own token for that service and never passes the client's token on ([Never pass a client's token through](#no-token-passthrough)).

## Validate the issuer of each response {#validate-the-issuer}

Binding the audience, as [Bind each token to one server](#token-audience) does, keeps a token from working at the wrong server. A mix-up attack strikes earlier, at the authorization code. A host that talks to several authorization servers sends each code to whichever server it believes answered. In a mix-up, an attacker's authorization server gets the host to start a flow with it, then sends the user's browser on to an honest authorization server. The honest server's code arrives at the host's redirect URI. The host, still believing it is talking to the attacker, sends the code to the attacker's token endpoint. PKCE alone doesn't stop this, "because the client transmits the `code_verifier` to the attacker's token endpoint" ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). Nor does `resource`, which the attacker rewrites in the request it forwards.

The defence is the `iss` parameter of RFC 9207. The authorization server names itself in its redirect, and the client compares that name with the server it sent the user to. The pinned revision introduced this check ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Before redirecting, the client records the issuer from the authorization server's validated metadata, and it compares `iss` with that record by exact string comparison, with no normalisation of case, ports or slashes ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)).

The rules are conditional. Authorization servers SHOULD include `iss`, and one that does MUST advertise `authorization_response_iss_parameter_supported`. A client MUST compare an `iss` that is present, whatever the metadata says, and MUST reject a response without `iss` only when the server advertised support. Otherwise it proceeds. On a mismatch, the client must not act on or display any `error` in the response. The specification expects a later revision to make `iss` a MUST for authorization servers ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). Comparing a present `iss` that wasn't advertised uses the latitude RFC 9207 leaves to local policy, and its default is that clients SHOULD discard such a response ([RFC 9207, section 2.4](https://www.rfc-editor.org/rfc/rfc9207.txt)).

The attacker in this case is the partner. The attack is set up with `MixUp` from `lib.auth_server`. The partner's MCP server names the attacker's authorization server, which copies the metadata of the shop's authorization server without `iss` support. Its authorization endpoint forwards the browser to the shop's authorization server, carrying the host's own request rewritten to ask for the shop's server and every scope. The host's client ID is a metadata document URL, which works with any authorization server, so the shop's authorization server sees a request from the real support host.

[Run a mix-up attack against the host](../examples/mix-up-attack-blocked.py)

The attack runs twice, against a shop authorization server that sends `iss` and against one that doesn't, and each run prints what the host saw and what the attacker got. In both runs the user consented at the shop's authorization server, because the request in front of them came from the real support host. When the shop sends `iss`, the answer carried the shop's issuer, the SDK stopped with `{{out:mix-up-attack-blocked:shop sends iss, host stopped}}`, and the attacker received no codes. When the shop omits `iss`, the answer carried none, and the SDK went on, as the specification says it should for a server that never advertised `iss`. The attacker received {{out:mix-up-attack-blocked:shop omits iss, codes the attacker received}} code with its verifier, redeemed it at the shop's authorization server, and holds a token for the shop's server with the scope `{{out:mix-up-attack-blocked:shop omits iss, attacker's token scope}}`, refunds included. The host saw only `{{out:mix-up-attack-blocked:shop omits iss, host stopped}}`.

So the check protects a host only when the honest server sends `iss`. The security best practices say the check gives no protection against an honest server that omits `iss` ([security best practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)). The SDK follows the specification's table exactly (`validate_authorization_response_iss` in `mcp/client/auth/utils.py`). Whether the shop's tokens can be stolen this way therefore depends on the shop's authorization server, not on the host. The other defence RFC 9700 describes, a distinct redirect URI for each authorization server, doesn't help this host. RFC 9700 says it "cannot be used in scenarios where clients only register once for the use of many different issuers", and it should be used only when nothing else is available ([RFC 9700, section 4.4.2.2](https://www.rfc-editor.org/rfc/rfc9700.txt)). A client identified by a metadata document is that case, with one `client_id` and one list of redirect URIs for every authorization server, so the honest server accepts whichever listed URI the attacker forwards. What a host can do without the server's help is limit which authorization servers it uses at all. An attacker's server that isn't on the host's allow-list never starts a flow.

**Working rule:** Send `iss` from every authorization server you run, and advertise it with `authorization_response_iss_parameter_supported: true`, so that clients reject an answer without it. In a host, keep the SDK's check, add no normalisation around it, and treat a mismatch as an attack: show the user none of that response's error text. When a host must use an authorization server that doesn't send `iss`, keep the host to an allow-list of authorization servers, and refuse or warn the user about any server not on it. Don't count on a separate redirect URI per server when the host is identified by a metadata document.

## Scope tools by what the token allows {#scopes-per-tool}

With a token checked as [Bind each token to one server](#token-audience) and [Validate the issuer of each response](#validate-the-issuer) describe, the shop's server knows who is calling. It still has to decide what each caller may do. The token lists the scopes the user granted, and the shop has three: `orders:read` for finding, reading and quoting orders, `stock:read` for checking stock, and `refunds:write` for issuing a refund, which only support leads may grant.

The SDK checks scopes per endpoint, not per tool. `AuthSettings.required_scopes` applies to every request, and the SDK's own 403 names no `scope` (`mcp/server/auth/middleware/bearer_auth.py`). The specification asks for a challenge a client can act on: a 403 with `WWW-Authenticate: Bearer error="insufficient_scope"`, the `scope` the operation needs and `resource_metadata`, with "all scopes required for the current operation in a single challenge" ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). An HTTP middleware can send that. At the pinned revision each `tools/call` names its tool in the `Mcp-Name` header, but servers MUST decode its `=?base64?...?=` form before comparing it with the body ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). A check on the raw header therefore lets an encoded `issue_refund` through. And a client at revision 2025-11-25, which the SDK's server still accepts on the same endpoint, sends no `Mcp-Name` at all.

So `lib.tool_scopes.require` decides on what the server will execute, with the credential the SDK will use: the tool named in the parsed body's `params.name`. The `Mcp-Name` header, decoded as the SDK decodes it, must match that name, or the request gets -32020, `HeaderMismatch`. A body that isn't one JSON object, or that repeats a key, is refused. The SDK authenticates with the first `Authorization` header (`bearer_auth.py`), so the middleware refuses two of them with 400 `invalid_request`. It reads the token through the SDK's own `BearerAuthBackend`, and it answers 401 to a tool call whose token doesn't verify.

The middleware denies by default. A tool missing from the map is refused. Methods that name nothing, such as `tools/list`, need only the endpoint's scopes, and any other method, such as `prompts/get`, `resources/read` or `tasks/get`, gets 403. `lib.protected_shop` maps all five tools, and `lib.tool_scopes.hide_unscoped` can hide the tools a token can't call ([Keep the tool list small](#keep-the-tool-list-small)). Signing a token with only the two read scopes lets the example list the tools with hiding off and on, and then send hand-written calls.

[Require refunds:write for refunds](../examples/refund-needs-a-scope.py)

The refund is refused for its scope, which the server reads from the body. `get_order_status` got {{out:refund-needs-a-scope:get_order_status}}, and `issue_refund` got {{out:refund-needs-a-scope:issue_refund}}, with the challenge `{{out:refund-needs-a-scope:challenge}}`. That challenge names `refunds:write` and carries a `resource_metadata` URL, as an assert checks.

With hiding off, the token sees every tool, including `issue_refund`. With hiding on, `issue_refund` is missing. Either way the list's cache scope is `{{out:refund-needs-a-scope:tools/list cacheScope}}`, the SDK's default, which suits a list that depends on the token ([Cache list results](#cache-list-results)).

The header checks fail where the body check holds. A refund whose `Mcp-Name` claimed `get_order_status` got {{out:refund-needs-a-scope:issue_refund named get_order_status in Mcp-Name}}. Two requests that a check on the header alone would pass were refused for scope. The refund with `Mcp-Name` in Base64 got {{out:refund-needs-a-scope:issue_refund with Mcp-Name in base64}}, and the refund from a client at 2025-11-25 got {{out:refund-needs-a-scope:issue_refund at 2025-11-25}}.

A refund that sent the read-only token and then a junk second `Authorization` header got {{out:refund-needs-a-scope:issue_refund with two Authorization headers}}. A check that read the last header would have let the SDK refund on the read-only token. An unmapped `prompts/get` got {{out:refund-needs-a-scope:prompts/get, which no scope maps}}. With `refunds:write`, the call reached the tool, which answered {{out:refund-needs-a-scope:issue_refund with a lead token}}: the status, then the result's `isError`, true because the quote ID doesn't exist.

**Working rule:** Map every tool to its scopes, and authorize on the parsed request with exactly the credential the SDK authenticates, never on a header alone. Refuse two `Authorization` headers, and any method your map doesn't cover. Treat `Mcp-Name` as a hint that must match the body once decoded, and refuse any body you can't parse exactly as the server does. Answer a missing scope with a 403 `insufficient_scope` challenge that names all of the tool's scopes, and keep `required_scopes` to what every request needs.

### Ask for more scope when a call needs it {#step-up-scopes}

The 403 in [Scope tools by what the token allows](#scopes-per-tool) is half of step-up, and the client does the other half. On `insufficient_scope`, the client authorizes again with the union of the scopes it asked for before and the scopes in the challenge, retries, and limits how many times it tries ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). The union rule is in the pinned revision's text and not in revision 2025-11-25's ([2025-11-25 authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)). Without it, a client that asked for `refunds:write` alone would lose `orders:read`, and its next order lookup would start the cycle again. The SDK's client steps up on 403 and unions the scopes (`mcp/client/auth/oauth2.py`).

A support lead and a member of the support staff without the lead role each refund order O-1004 through the SDK's client. The refund, €{{out:step-up-for-refunds:lead, quote amount}}, is within the policy limit, so no confirmation is involved. The scripted consent lets the lead grant all three scopes, and the other user only the two read scopes.

[Step up to refunds:write](../examples/step-up-for-refunds.py)

The lead's first authorization asked for the two read scopes. The refund's 403 started a second, which asked for `{{out:step-up-for-refunds:lead, authorization 2 asked for}}`, the union, although the challenge named only `refunds:write`. The retry went through, and the refund's status is `{{out:step-up-for-refunds:lead, refund status}}`. For the other user, the second authorization asked for the same union. The user could grant only `{{out:step-up-for-refunds:non-lead, token scope}}`, and the retried call failed with `{{out:step-up-for-refunds:non-lead, refund failed}}`. The SDK stepped up once and stopped, so there was no loop. But the host got a generic error, not "this needs a lead".

**Working rule:** Let the SDK step up, and keep its union of scopes. List every tool a caller could gain by step-up, since a hidden tool never gets the 403 that starts the step-up. When a host compares the scope the token response granted with the scope the challenge asked for, and they differ, it should treat that as a decision, not a fault: tell the user which scope the call needs, and pass the ticket to someone who holds it. Never let an authorization server grant by step-up what a user's role doesn't allow. The client only asks, and the authorization server decides.

## What goes wrong in production {#authorization-in-production}

The shop's server, its authorization server and its host all work on loopback. In production they meet other people's authorization servers, gateways and clients, and each of these failures has a sign you can watch for.

**An authorization server that doesn't send `iss`.** It is a SHOULD at the pinned revision, so some authorization servers leave it out, and the SDK then proceeds without any defence against mix-up ([Validate the issuer of each response](#validate-the-issuer)). The sign is metadata without `authorization_response_iss_parameter_supported`. Check the metadata of each authorization server your host meets, and keep the host to an allow-list of authorization servers while any of them leaves `iss` out.

**The silent fallback to registration.** When an authorization server doesn't advertise Client ID Metadata Document support, the SDK registers dynamically without saying so ([OAuth clients](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.3.0/docs/client/oauth-clients.md)). The sign is registration errors, or a growing list of registered clients at the authorization server. Log which kind of client ID each connection used.

**The audience check is off.** A server without `validate_token_resource` accepts tokens issued for other servers, and the only sign is an `MCPDeprecationWarning` at startup ([Bind each token to one server](#token-audience)). Make warnings from `AuthSettings` fail the deployment.

**An issuer with a trailing slash.** The issuer comparison is by exact string, so `https://auth.fernhill.example` and `https://auth.fernhill.example/` are different issuers, and the SDK raises "Authorization server metadata issuer mismatch". The SDK's metadata models keep a URL without a path as it was sent, but an `AnyHttpUrl` object built in Python still gains the slash. Pass URLs to the SDK as strings ([SDK migration guide](https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/v2.3.0/docs/migration.md)). The sign is `OAuthFlowError` on the first connection to a server, from every host.

**No PKCE check in the host.** The SDK's client never reads `code_challenge_methods_supported` ([Get a token with PKCE](#authorization-code-with-pkce)). Nothing fails, so the only sign is an audit: fetch each authorization server's metadata and look for `S256`.

**A `localhost` redirect taken over.** A metadata document proves which domain a client belongs to, not which program listens on a `localhost` redirect URI, and any local program can bind the port first. The specification says that metadata documents "cannot prevent `localhost` URL impersonation by themselves", and it asks authorization servers to show the redirect's host name to the user and to warn about redirects to `localhost` ([security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)). The sign is a consent screen that names the real host for a request no one at that machine made.

**An authorization server used to probe the network.** A server that fetches any client ID URL can be pointed at internal addresses. The draft says authorization servers MUST NOT fetch from special-use addresses, with a loopback exception only for development servers that themselves run on loopback ([metadata document draft -02, section 8.6](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.txt)). The sign is metadata fetches to private addresses in the authorization server's logs.

**Consent every few minutes.** The shop's authorization server issues no refresh token, so the host runs the whole flow again whenever a token expires, and the user consents again. If you issue refresh tokens to hosts, which are public clients, the authorization server MUST rotate them. MCP servers SHOULD NOT list `offline_access` in their challenges or `scopes_supported` ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). The sign is authorization requests from one host at the token lifetime's interval.

**Step-up that can never succeed.** A server whose 403 names a scope the authorization server doesn't know, or one the user's role can't grant, sends every such call through a second authorization that fails. The sign is authorization requests in pairs for one tool call, followed by a generic error in the host ([Ask for more scope when a call needs it](#step-up-scopes)).

**Working rule:** Before the shop's server takes traffic, run three probes against the deployment. A request without a token gets 401 with a `resource_metadata` URL. A token for another resource gets 401. A refund with a read-only token gets 403 with `scope="refunds:write"`, and the same refund with a second `Authorization` header gets 400. Then check the metadata of every authorization server your hosts use for `S256`, `iss` support and metadata document support, and watch the 401s, 403s and authorization requests per host.

## Decisions this chapter made {#authorization-decisions}

- **The shop's server is an OAuth resource server** over Streamable HTTP, configured with the SDK's `AuthSettings`: its endpoint's URL as `resource_server_url`, `orders:read` and `stock:read` as `required_scopes`, and `validate_token_resource=True`.
- **Every example uses a teaching authorization server,** `lib.auth_server`, not the SDK's built-in one: S256 only, `resource` required, `iss` sent and advertised, single-use codes, JWT access tokens with `aud` and `scope`, and no refresh tokens. A deployment uses an established authorization server with the same properties.
- **The support host is identified by a Client ID Metadata Document** at an `https://` URL on `support.fernhill.example`. In the examples the authorization server holds a local copy of the document in place of fetching it, and Dynamic Client Registration isn't offered.
- **Hosts use the SDK's `OAuthClientProvider`** with `client_metadata_url`, and add the PKCE support check the SDK leaves out.
- **Tokens are checked for audience** by `AuthSettings`, and the token verifier reports `aud` as `AccessToken.resource`.
- **Scopes are per tool:** `orders:read` for finding, reading and quoting orders, `stock:read` for stock, and `refunds:write`, which only support leads can grant, for refunds. An HTTP middleware decides on the parsed JSON-RPC body, with `Mcp-Name` only as a hint that must match it, and with the one token the SDK authenticates, refusing a second `Authorization` header. It answers a missing scope with a 403 challenge, and refuses tools and named methods that it doesn't map.
- **`refunds:write` arrives by step-up,** never by default. It isn't in `scopes_supported`, and the SDK's client asks for the union of scopes when a refund needs it.
- **Every tool stays in `tools/list`,** so that step-up can start. Hiding tools by scope is available in `lib.tool_scopes` and unused.
- **Who the host acts for comes from the verified token's `sub`,** through `get_access_token()`, never from a tool argument: for the support host, a member of the staff. The customer a ticket concerns comes from the ticket record, which the server looks up and checks, not from the token or an argument. Only where customers sign in is `sub` the customer.
