# MCP end to end

By the end of this chapter you can put an existing HTTP API behind a Model Context Protocol server over stdio, call its tool from a client, read every message the two exchange, and let a model choose the tool through a small host. Every example runs on one machine, against revision {{out:call-order-status:protocol revision}} of the specification and the Python SDK, `mcp` {{version:mcp}}.

A customer writes to Fernhill Supply, an online store for kitchen and garden goods, to ask where an order is. The answer lives in the store's systems, not in the ticket, so a model in the support team's host can answer only if something lets it look the order up. This chapter takes on that problem, and [Meet the shop and its API](#the-shop) introduces the store in full.

The Model Context Protocol (MCP) is how an application that uses a model gets tools and data from programs it didn't write. The **host** is the application the user works in, such as a support desk or a coding assistant. A **client** is the host's connection to one server. A **server** exposes capabilities, such as tools a model can call ([specification overview](https://modelcontextprotocol.io/specification/2026-07-28)). The messages between a client and a server are JSON-RPC 2.0.

This chapter builds a rough version of the whole thing: an API, a server with one tool, a client, a trace of the wire and one recorded choice by a model. Each later chapter makes one of those parts solid.

## Meet the shop and its API {#the-shop}

An MCP server rarely starts from nothing. Most teams that need one already run an HTTP API with its own data, authentication and clients, and the server's job is to put part of that API in front of a model. So the first thing to have is the API you're wrapping, running where your examples can reach it.

Every chapter works on the same store, Fernhill Supply, and we call it **the shop**. The shop is fictional and stands for no real business; its domain, `fernhill.example`, is a reserved name that can never resolve. Its support team answers customer tickets, and most tickets need a lookup in the shop's systems: where an order is, whether a product is in stock, or how much a refund would come to. The book's goal is a host that reads those tickets and calls the shop's tools to answer them.

The shop already has the "before" that every chapter wraps: **the shop's API**, an HTTP API for orders, stock and refunds that checks an API key in the `X-API-Key` header. Its records are **the shop's data**, generated by the book's own code from one fixed seed, so every run sees the same customers, orders and tickets. Three shared modules in `examples/lib/` hold this setup, so the examples stay short:

- `lib.shop_data` generates the shop's data. `load_shop()` returns its customers, products, stock levels, orders, refunds and tickets as Python dataclasses.
- `lib.shop_api` is the shop's API, a Starlette app over that data.
- `lib.loopback` serves an app on 127.0.0.1 on a free port and stops it when the block ends.

The first example starts the shop's API on loopback and calls it three ways: with the key, without it, and for an order that doesn't exist.

[Start the shop's API and call it](../examples/start-the-shop-api.py)

The generator's seed is {{out:start-the-shop-api:seed}}, and the output beside the example counts the customers, products, orders and tickets it produces. Emails are at `example.com`, phones are masked to two digits, and payment shows only "card ending" with the last four digits of a published test card. The data card in `examples/data/shop/README.md` lists every field.

The API's answer depends on the key, and that answer is the contract the MCP server has to respect. With the key, it answers {{out:start-the-shop-api:with key}}: order O-2476 is {{out:start-the-shop-api:order status}}, shipped on {{out:start-the-shop-api:shipped on}}, for a total of €{{out:start-the-shop-api:total}}.

Without the key it answers {{out:start-the-shop-api:without key}}, and an order that doesn't exist gets {{out:start-the-shop-api:unknown order}}. The shop prices everything in euros, and its API sends amounts as plain decimals with no currency code. The server will hold the key, call the same endpoint, `GET /orders/{order_id}`, and turn its answers into something a model can read; it won't reimplement orders.

**Working rule:** Wrap the API you already run, and keep it the system of record. The MCP server should be a thin adapter that calls the API with its own credentials and translates the answers, so the API's validation, authorization and logs keep working for every client, not only for models. Build directly on the database only when there is no API to wrap, and even then put the business rules in one place that both kinds of client share.

## Wrap one endpoint as a tool {#wrap-an-endpoint-as-a-tool}

The shop's API from [the previous section](#the-shop) answers "what is the status of order O-2476" for any HTTP client. To answer that for a model, the shop needs an MCP server that exposes the lookup as a **tool**: a named action with a description and a JSON Schema for its inputs, which a model can decide to call ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The server publishes its tools in `tools/list`, and a client runs one with `tools/call`.

In the Python SDK the server class is `MCPServer`, imported from `mcp.server.mcpserver`. The SDK's 1.x releases called it `FastMCP`, and at {{version:mcp}} importing `mcp.server.fastmcp` fails with a pointer to the [migration guide](https://py.sdk.modelcontextprotocol.io/v2/migration/). You register a tool with the `@server.tool()` decorator, called with its parentheses; the bare `@server.tool` raises a `TypeError` that asks for them ([`mcp` source](https://pypi.org/project/mcp/2.3.0/), `mcp/server/mcpserver/server.py`). The SDK reads the tool's name from the function's name, its description from the docstring and its input schema from the type hints. `server.run()` serves over **stdio**, the transport in which the client starts the server as a subprocess and the two exchange messages on its standard input and output, and stdio is `run()`'s default.

The shop's first server is called `shop-orders`, and its one tool, `get_order_status`, wraps `GET /orders/{order_id}`. It reads the API's address and key from its environment, so they never appear in the code or on the wire. Server examples follow one pattern: the file defines the server, and run with no arguments it starts a client that launches the same file with `--serve`. Here that client lists the tools.

[A server with one tool, get_order_status](../examples/order-status-server.py)

What the client sees is the tool's definition. Its name is `{{out:order-status-server:tool}}`, its description is the docstring word for word, and its input schema says that `order_id` is a required string. The SDK built that schema from the `order_id: str` hint and added `title` fields of its own, such as `"Order Id"`. The model reads only the description and the schema, so the docstring is written for a model: what the tool does, what an ID looks like and what comes back. [Write descriptions the model reads](#write-tool-descriptions) measures how much that wording matters.

Two details decide how the tool behaves under load and when it fails. The function is a plain `def` that makes a blocking HTTP call, and at {{version:mcp}} the SDK runs synchronous tools on a worker thread, so a slow call to the shop's API doesn't stall the server's other requests ([migration guide](https://py.sdk.modelcontextprotocol.io/v2/migration/)). The function also raises `ToolError` when the API answers 404, and the SDK passes a `ToolError`'s message to the client as a failed tool result. Any other exception becomes a generic `Error executing tool` message, and its own text stays on the server (`mcp/server/mcpserver/tools/base.py`). [Call the tool from a client](#call-a-tool-from-a-client) shows both kinds of failure.

The HTTP client is `httpx2`, a fork of HTTPX that the SDK itself depends on at {{version:mcp}} ([migration guide](https://py.sdk.modelcontextprotocol.io/v2/migration/)), so the server needs no HTTP library of its own. The tool uses only `httpx2.get()`, the response's `status_code`, `raise_for_status()` and `json()`, .

**Working rule:** Start with one read-only tool that maps to one endpoint, and write its docstring for a model: what it does, what its inputs look like, what it returns. Raise `ToolError` with a message that tells the model what to do differently, and let unexpected exceptions stay generic so internal details never leave the server. Once you wrap more than a handful of endpoints, shape the tools around the tasks the model has to do rather than one per endpoint ([Shape tools around tasks, not endpoints](#tasks-not-endpoints)).

## Call the tool from a client {#call-a-tool-from-a-client}

The `shop-orders` server from [the previous section](#wrap-an-endpoint-as-a-tool) runs only when something launches it. In the shop's case that something is the host, and the part of the host that talks to one server is a client. Over stdio, a client starts the server as a subprocess, writes requests to its standard input and reads responses from its standard output ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)).

At the pinned revision there is no handshake and no session. Each request stands alone and carries the protocol version and the client's capabilities in its `_meta` field, and the specification says a server "MUST NOT rely on prior requests over the same connection to establish context" ([base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic)). The same page also says an open connection, such as a stdio process, isn't a conversation or a session. Revisions up to 2025-11-25 opened every connection with an `initialize` handshake; [Remove initialize and session IDs](#remove-sessions) covers moving off it.

The Python SDK's high-level client is `mcp.Client`. Given a `StdioServerParameters`, it launches that command as a subprocess. By default it runs in `mode="auto"`: it first sends `server/discover` at the pinned revision, and falls back to the old `initialize` handshake whenever the probe times out or fails with any error except a `-32022` whose list of versions shares none with the client's ([Handle a version the server doesn't support](#version-mismatch)) (`mcp/client/client.py`, `mcp/client/_probe.py`). A 2025-era server answers `server/discover` with an error, so it gets the old handshake. Use `Client` rather than building a low-level `ClientSession` and calling `initialize()` on it yourself, which always speaks the pre-2026 handshake ([migration guide](https://py.sdk.modelcontextprotocol.io/v2/migration/)).

Two settings matter more than they look. The command is `sys.executable`, the Python running the example, rather than `"python"`, so the server starts in the same environment with the same pinned packages, whatever is first on the `PATH`. The shop API's address and key go in `env=` explicitly, because the stdio client doesn't pass the parent's environment through: on Linux and macOS it passes only `HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM` and `USER`, plus what you give it (`mcp/client/stdio.py`). The client also names itself, `shop-host`, so the server's logs and the wire show who called.

Three calls follow: one for a real order, one for an order ID that doesn't exist, and one from a second client that forgets the environment.

[Call get_order_status over stdio](../examples/call-order-status.py)

The client and the server agreed on revision {{out:call-order-status:protocol revision}}, and the client learned the server's name and version, `{{out:call-order-status:server}}`, from the `server/discover` answer. The first call succeeds: its result is not an error, and the order's status is {{out:call-order-status:order status}}, the same answer the shop's API gave directly.

The wrong ID, O-7144, comes back as a result, not an exception. Its result is flagged as an error, and its text is the `ToolError` message, prefixed by the SDK. A model that reads "Order IDs look like O-1873" can ask the customer again. The third call fails differently. The server started without `SHOP_API_URL`, so the tool raised a `KeyError`, and all the client got was `{{out:call-order-status:without env says}}`. The `KeyError` itself went to the server's standard error, where an operator can find it and a model can't. That split is deliberate: a missing variable shows up in the server's logs, never in the conversation.

**Working rule:** Connect with `mcp.Client`, launch stdio servers with `sys.executable` and an explicit `env=`, and give the client a name. Pass each variable the server needs, and nothing else from your own environment, so a server never sees secrets meant for another program. When a tool fails with only the SDK's generic message, read the server's standard error before you change the client.

## Read the messages on the wire {#read-the-messages}

The client in [the previous section](#call-a-tool-from-a-client) hid every message behind `call_tool()`. When a server misbehaves, or you need to know what the pinned revision really sends, read the messages themselves. Over stdio, each message is one line of JSON-RPC on the server's standard input or output, with no embedded newlines. The server must not write anything to its stdout that isn't a valid MCP message, and its logs belong on standard error ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)).

A faithful trace needs a real subprocess. The SDK's in-process client, `Client(server)` given a server object, dispatches calls directly in its default auto mode and sends no JSON-RPC at all (`mcp/client/client.py`), so it can't show you the wire. The book's trace printer, `lib.wire`, puts a small relay between the client and the server instead: the client launches the relay, the relay launches the real server, and the relay copies every line in both directions unchanged while appending it to a log.

`wire.print_trace()` then prints that log in order, with numbered messages, arrows for direction (`->` from client to server, `<-` back) and request IDs renumbered so the output stays stable. Values under names that look like secrets print as `[redacted]`; this trace has none.

Next, the trace of that same call for order O-2476: three messages print in full, and three on one line each.

[Trace one tool call on the wire](../examples/trace-first-call.py)

Nothing in this exchange is a handshake. The whole exchange is {{out:trace-first-call:messages}} messages, and the methods, in order, are {{out:trace-first-call:methods}}. Reading them one at a time:

1. **`server/discover`** is the first request. Its `params` hold only `_meta`, with three entries: the protocol version, `clientInfo` naming `shop-host`, and `clientCapabilities`, which is empty because this client declares none. Every server must implement `server/discover` ([discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)).
2. **Its result** lists `supportedVersions` and the server's `capabilities`, and the server's own `_meta` carries its `serverInfo`. The result also has `resultType` and two cache hints, `ttlMs` and `cacheScope`, which [Cache list results](#cache-list-results) explains.
3. **`tools/list`** carries the same `_meta` again, since nothing from the first exchange is assumed.
4. **Its result** holds the tool definition that [the server example](#wrap-an-endpoint-as-a-tool) printed.
5. **`tools/call`** names the tool and gives its `arguments`, and once more carries the protocol version, the client's name and its capabilities.
6. **Its result** holds the order as text `content`, with `isError` set to false and `resultType` set to `"complete"`.

Every result carries `resultType`, and `"complete"` marks an ordinary answer. The other kind, a request for input in the middle of a call, is the subject of [Return an input request instead of a result](#return-an-input-request). A client treats a result without the field, from an older server, as complete ([base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic)). The SDK's server adds both `resultType` and the `serverInfo` stamp itself (`mcp/server/runner.py`).

One thing is missing from the trace on purpose: the shop's API key. It reached the server through the subprocess's environment, and the server sent it only to the shop's API. That is how the specification wants stdio servers to get credentials, by retrieving them from the environment, rather than by following the OAuth flow that [Authorize clients with OAuth](#authorization) teaches for HTTP ([base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic)).

**Working rule:** When a call behaves in a way you don't expect, trace the wire before you read the SDK's code: a relay that copies lines and logs them works with any client and any server. Never write to standard output from a stdio server, not even a debugging `print()`, because the client reads every line there as a message. Use `logging`, which the SDK sends to standard error, or write to standard error yourself.

## Let a model choose the tool {#let-a-model-choose}

Until now, the example code chose the tool and its arguments. In the shop's case a model should make that choice. Tools are model-controlled: the host shows a model the available tools, and the model decides which to call and with what arguments ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The host stays in charge of everything else. It builds the prompt, reads the model's reply, makes the call through its client, and decides what to do with the result.

The book's host loop, `lib.host`, is a small host the book writes itself, so you can see each of those steps. In this chapter it does one turn. It renders the server's tools into the book's own system prompt, giving each tool's name, description and input schema, then sends that prompt and one ticket to a model and parses the reply. A reply holding a `<tool_call>` block with a tool's name and arguments is a choice; any other reply is an answer in words. The prompt and the parsing stay in the book's code, not a model library's, so the same code drives the real model when a recording is made and the replay in examples.

Examples in this book never call a model, because a model's output isn't deterministic and examples must run offline. A **recording** holds the model's raw replies under `examples/data/recorded/`, made once by a script in `recordings/`, and examples replay them with `ReplayModel`. That replay answers only for the exact messages it recorded, and it fails loudly if the prompt, the ticket or the tools have changed. The model for every recording in this book is Qwen3-4B-Instruct-2507, an open model under the Apache-2.0 licence, quantized to 4 bits (Q4_K_M, in a third-party GGUF conversion) and run on the CPU with llama.cpp, so anyone can make the recordings again. The script `recordings/pick_a_tool.py` made this chapter's recording, `pick-a-tool`, against the same server and prompt, and its manifest names the model file by revision and hash.

Three of the shop's tickets go to the model here. One quotes an order ID the way the shop writes it, one gives a bare order number, and one asks about stock, which no tool on this server can answer.

[The host lets a model pick a tool](../examples/host-picks-a-tool.py)

On ticket T-0003 the model chose the tool that answers it, `{{out:host-picks-a-tool:T-0003 tool}}`, for order {{out:host-picks-a-tool:T-0003 order id}}, and the host's call found the order {{out:host-picks-a-tool:T-0003 order status}}. Ticket T-0010 gave only a bare number, and the model still sent {{out:host-picks-a-tool:T-0010 order id}}, the form both the description and the prompt show. For the stock question in T-0015, the model called no tool and said in words that it couldn't check stock. That is the right behaviour for a server that offers only order lookups, and chapter 3 adds the `check_stock` tool the ticket needs.

Three recorded choices show the loop working. They don't measure how often a model chooses well: [Write descriptions the model reads](#write-tool-descriptions) compares descriptions on more tickets, and [Measure how often the right tool is chosen](#tool-selection-accuracy) measures accuracy over the whole ticket queue.

This host calls `get_order_status` without asking anyone, and that departs from the specification. The specification puts consent on the host: hosts "must obtain explicit user consent before invoking any tool", and MCP itself can't enforce that ([specification overview](https://modelcontextprotocol.io/specification/2026-07-28)). The tools page adds that a human should be kept in the loop, able to deny a tool call ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). We skip it here because the tool only reads, from a server the shop runs itself, so a wrong call changes nothing; we'd skip it only in that case. [Ask for consent before side effects](#consent-before-side-effects), in the chapter on MCP's security model, adds the consent step.

**Working rule:** Keep the host's prompt and the parsing of the model's reply in your own code, and test the loop against recorded replies rather than a live model. Record the model's raw text, not SDK objects, so an SDK release doesn't invalidate a recording, and make a replay fail when its input changes. Switch to a live model only for the measurement runs that decide which descriptions and which model you ship.

## What goes wrong in production {#mcp-end-to-end-in-production}

In production the same few parts fail in a handful of ways, each with a sign you can watch for.

**Anything on standard output breaks the channel.** A library that prints a banner, or a stray `print()` while debugging, puts a line on the server's standard output that isn't JSON-RPC, and the stdio transport forbids it ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)). You notice it as parse errors or dropped responses in the client, often only on the one code path that prints. The SDK's own logging goes to standard error (`mcp/server/mcpserver/utilities/logging.py`), so route yours there too.

**The server inherits less than you think.** The stdio client passes a short allowlist of variables and nothing else (`mcp/client/stdio.py`), so a server that works from your shell fails when a host launches it. The sign is the one [the client example](#call-a-tool-from-a-client) showed: a generic `Error executing tool` in the client and a `KeyError` in the server's standard error. Pass every variable in `env=`, and fail at startup if one is missing rather than at the first call. The shop's server reads its variables inside the tool on purpose, so that the client example could show the late failure; a server you ship should read them once, before it serves.

**The server dies mid-call.** The specification asks the client to restart a stdio server that exits, and because the protocol is stateless, "any in-flight requests are simply lost and the client can retry them" ([stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)). `mcp.Client` doesn't restart anything at {{version:mcp}}: a call in flight fails with an `MCPError` that says `Connection closed`, and the host has to open a new `Client` and retry (`mcp/client/stdio.py`, `mcp/shared/jsonrpc_dispatcher.py`). A retried `get_order_status` is harmless. A retried refund isn't, which is why the shop's refund tool needs a once-only check on the server ([Keep round-trip state tamper-proof](#round-trip-state)). For shutdown, the client closes the server's standard input and waits; the SDK gives it 2 seconds before escalating to a signal (`mcp/client/stdio.py`), so servers should exit promptly on end of input.

**A slow start costs time and can change the revision.** The SDK's client waits 10 seconds for the answer to `server/discover` (`mcp/client/session.py`). A server that loads a large model or opens many connections before it reads its first message can miss that window on a cold machine. Auto mode doesn't give up then: it treats the timeout as a failed probe and sends the old `initialize` handshake, which has no default time limit (`mcp/client/_probe.py`). A server built on this SDK that has already answered the late probe rejects `initialize` with the versions it supports, and the client probes once more, so the connection succeeds more than 10 seconds late. A server from another SDK that also answers `initialize` can settle on a 2025 revision without any error. The sign is `client.protocol_version`, not a dead server. Do slow setup lazily, or after the server is reading its input.

**The other side speaks a 2025 revision.** `Client` in auto mode falls back to the old handshake for a 2025-era server. After a fallback the connection speaks the 2025 revision, so none of the pinned revision's features are there ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)), and `client.protocol_version` says which revision you got. A server that doesn't support the client's version answers with an error, which [Handle a version the server doesn't support](#version-mismatch) shows. When the error comes from someone else's server, the trace from [Read the messages on the wire](#read-the-messages) tells you which revision each side sent.

**Other languages lag or lead.** The MCP documentation lists official SDKs by tier. Tier 1 is TypeScript, Python, C#, Go, Rust and Ruby, and the tiers change over time ([SDKs](https://modelcontextprotocol.io/docs/sdk)). A host in one language and a server in another can implement a revision's details differently, and the wire is where you settle which one is right.

**Working rule:** Before a stdio server goes to production, check three things on the machine that will launch it: nothing but JSON-RPC reaches standard output, every variable the server needs is passed explicitly, and the server answers `server/discover` within 10 seconds of starting. Keep its standard error in your logs.

## Decisions this chapter made {#mcp-end-to-end-decisions}

- **The shop's data comes from one seed** and ends on a fixed date, so every example sees the same customers, orders and tickets.
- **The shop's API stays the system of record.** The MCP server is a thin adapter that calls it with its own key.
- **One read-only tool, `get_order_status`,** wraps one endpoint. Its docstring is written for a model.
- **Failures the model can act on raise `ToolError`;** every other exception reaches the client as a generic message and stays in the server's standard error.
- **stdio first,** with `MCPServer.run()`'s default transport. Streamable HTTP comes in [Serve over Streamable HTTP](#streamable-http).
- **`mcp.Client` in its default auto mode,** never a hand-initialized `ClientSession`, so the first message is `server/discover` at the pinned revision.
- **Servers launch with `sys.executable` and an explicit `env=`,** and credentials travel in the environment, never on the wire.
- **Traces come from a relay on a real stdio subprocess,** because the in-process client sends no JSON-RPC.
- **The host loop's prompt and parsing are the book's own code,** and examples replay recordings of Qwen3-4B-Instruct-2507, an open model run on the CPU.
- **A recording answers only the exact messages it saw.** A changed prompt, ticket or tool list fails the replay instead of returning a stale reply.
- **No consent step in this chapter,** a departure from the specification that we accept only for a read-only tool on a server the shop runs. Consent arrives in [Ask for consent before side effects](#consent-before-side-effects).
